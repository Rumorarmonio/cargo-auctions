# Техническое задание

## 1. Назначение документа

Этот документ переводит требования тестового задания и контракт `openapi.auctions.v0.json` в рабочую спецификацию для реализации SPA. Он используется как источник требований при разработке, проверке UI, настройке MSW и подготовке README.

Подтверждённые требования отделены от решений, которые ещё нужно принять.

## 2. Общая идея проекта

Нужно создать SPA для работы с грузовыми аукционами по готовой OpenAPI-схеме:

- просмотр списка аукционов;
- фильтрация и пагинация;
- просмотр детальной информации;
- просмотр истории ставок;
- установка или изменение своей ставки.

Backend писать не нужно. API должен быть реалистично замокирован через MSW и поддерживать изменение состояния после mutation.

## 3. Цель проекта

Получить локально запускаемое, аккуратное и адаптивное frontend-приложение, которое демонстрирует основные пользовательские сценарии аукциона и точно соблюдает контракты OpenAPI.

## 4. Scope проекта

### 4.1. Что входит в scope

- React-приложение на TypeScript и Vite.
- TanStack Router для маршрутизации.
- TanStack Query для загрузки, кэширования, prefetch и invalidation.
- React Hook Form + Zod для формы ставки и валидации.
- MSW для мокирования API.
- Feature-Sliced Design как принцип организации кода.
- Точечный клиентский UI-state через MobX или Zustand.
- Страница списка аукционов.
- Детальная страница аукциона.
- Страница или вкладка ставок.
- Режим установки ставки, открываемый по ссылке.
- Обработка loading, skeleton, empty, error и disabled-состояний.
- Адаптация под desktop и mobile.
- README с запуском и описанием проверки.
- `AI_USAGE.md` с описанием использования AI.

### 4.2. Что не входит в scope

- Реальный backend.
- Реальная авторизация и интеграция с пользователем.
- Реальная база данных или серверное хранение.
- Административная часть и создание аукционов.
- Управление справочниками городов через API.
- Полноценная дизайн-система, если она не нужна для данного интерфейса.

### 4.3. Поздние и необязательные расширения

- Дополнительные тесты чистой логики.
- Более сложные фильтры и сохранение пользовательских пресетов.
- Улучшенная анимация и расширенная доступность.
- Персистентность мокового состояния между перезагрузками.

## 5. Ближайшая цель реализации

Ближайший milestone — локально запускаемое приложение с рабочим вертикальным срезом:

1. список аукционов загружается через TanStack Query;
2. переход на detail работает через TanStack Router;
3. detail загружается по `auctionUuid`;
4. ставки загружаются отдельным запросом;
5. форма ставки вызывает mutation;
6. MSW-store обновляет связанные данные после успешной ставки.

## 6. Технологический стек

### 6.1. Обязательный стек

- React.
- TypeScript.
- Vite.
- TanStack Router.
- TanStack Query.
- React Hook Form.
- Zod.
- MSW.
- Feature-Sliced Design.
- MobX или Zustand для точечного клиентского UI-state.

### 6.2. Допустимые дополнительные зависимости

Компонентная библиотека, библиотека иконок, toast-уведомлений, дат и тестирования выбираются кандидатом при условии, что они не усложняют проверку проекта.

### 6.3. Ограничения и замечания по стеку

- Компоненты React должны находиться в файлах с суффиксом `*.component.tsx`.
- API-контрактом считается `openapi.auctions.v0.json`, а не произвольная форма моковых данных.
- Нельзя подменять TanStack Query обычными локальными fetch-вызовами для серверного состояния.
- Моковые handlers должны поддерживать не только чтение, но и изменение состояния.

## 7. Функциональные требования

### 7.1. API-контракт

Использовать следующие endpoint’ы:

| Метод | Endpoint | Назначение |
|---|---|---|
| `POST` | `/auctions/list` | Список аукционов с фильтрами и пагинацией |
| `GET` | `/auctions/{auctionUuid}` | Детальная информация об аукционе |
| `GET` | `/auctions/{auctionUuid}/bets` | История ставок |
| `POST` | `/auctions/{auctionUuid}/bets` | Установка ставки |

Для endpoint’ов должны обрабатываться предусмотренные схемой успешные ответы и ошибки `401`, `404`, `422`, `503` там, где они описаны.

### 7.2. Список аукционов

Страница списка должна обеспечивать:

- загрузку через TanStack Query;
- пагинацию;
- skeleton/loading state;
- empty state;
- error state;
- prefetch detail по intent/hover;
- фильтры с синхронизацией в URL search params либо в localStorage;
- Zod-валидацию search params с безопасными fallback-значениями;
- desktop/mobile layout.

Поддерживаемые фильтры:

- `cargo_num`;
- `status`;
- `statuses`;
- `auc_type`;
- `load_city`;
- `unload_city`;
- дата погрузки от/до;
- `is_available`;
- `is_bidder`;
- цена от/до.

Города берутся из локального мок-словаря, поскольку отдельный API endpoint городов не предусмотрен.

### 7.3. Карточка аукциона

Карточка должна показывать:

- номер заявки;
- тип аукциона: `Request`, `Up`, `Down`, `FixPrice`;
- статус аукциона;
- торговый статус пользователя, например `Leading`, `Losing`, `Winner`;
- маршрут погрузка → выгрузка;
- даты погрузки и разгрузки;
- груз: название, вес, объём, тип кузова;
- текущую цену;
- цену за километр;
- шаг ставки;
- наличие своей ставки;
- primary action: «Сделать ставку», «Изменить ставку», «Смотреть ставки» либо disabled-состояние.

### 7.4. Детальная страница

Детальная страница должна использовать `GET /auctions/{auctionUuid}` и показывать:

- основные данные аукциона;
- организатора;
- контакты, если они не скрыты;
- маршрут со всеми точками;
- груз и требования к транспортному средству;
- условия оплаты;
- параметры торгов;
- текущую и доступную цену;
- `min`, `max`, `step`, если они присутствуют в DTO;
- состояние своей ставки.

Необходимо учитывать ограничения из detail DTO:

- `can_set_bet`;
- `hide_bets_history`;
- `hide_points_address_and_contacts`;
- `no_view_cargo_price`.

### 7.5. История ставок

Страница или вкладка ставок должна использовать `GET /auctions/{auctionUuid}/bets` и показывать:

- список ставок;
- количество участников;
- цену с НДС и без НДС;
- перевозчика;
- место в рейтинге;
- признак победителя;
- признак отменённой ставки;
- причину отмены, если она есть;
- empty state при отсутствии ставок;
- отдельное состояние при `hide_bets_history`.

### 7.6. Установка ставки

Форма «Сделать ставку» должна:

- быть доступной только при `trading.can_set_bet`;
- использовать React Hook Form + Zod;
- требовать цену больше нуля;
- учитывать `min`, `max`, `step`, если они есть в detail DTO;
- показывать подсказку по доступной цене и шагу ставки;
- вызывать `POST /auctions/{auctionUuid}/bets`;
- после успеха инвалидировать list/detail/bets queries;
- показывать success/error toast;
- обрабатывать `422 validation error`.

После успешной mutation MSW-store должен обновить:

- текущую цену;
- статус пользователя;
- список ставок.

## 8. Архитектурные принципы

- Разделять серверное состояние, UI-state и состояние формы.
- Типы и request/response-модели выводить из OpenAPI-контракта или поддерживать синхронными с ним.
- Query keys должны быть стабильными и учитывать параметры списка.
- Парсинг search params должен быть отдельной чистой логикой с безопасными fallback-значениями.
- UI-компоненты не должны напрямую знать детали MSW.
- MSW-store должен имитировать серверное состояние, а не быть глобальным UI-state.
- Маппинг DTO в ViewModel рекомендуется держать отдельно от компонентов.
- Все названия React component-файлов должны иметь суффикс `.component.tsx`.

## 9. Требования к структуре проекта

Рекомендуется использовать слои Feature-Sliced Design:

- `app` — запуск приложения, providers, router;
- `pages` — страницы списка, detail и ставок;
- `widgets` — крупные блоки страниц;
- `features` — фильтры, установка ставки, prefetch detail;
- `entities` — аукцион и ставка;
- `shared` — API-клиент, UI, утилиты, типы;
- `mocks` — MSW handlers, store и seed fixtures.

Рекомендуемые части mock-слоя:

- fixtures аукционов;
- fixtures ставок;
- словарь городов;
- изменяемый MSW-store;
- handlers для четырёх endpoint’ов;
- настройка browser/server worker;
- фабрики данных при необходимости.

## 10. Требования к стилям и UI-архитектуре

- Интерфейс должен быть аккуратным, читаемым и адаптивным.
- Desktop и mobile должны быть проверяемыми сценариями, а не только сжатием desktop-макета.
- Длинные маршруты, контакты, цены и статусы не должны ломать layout.
- Loading, empty, error и disabled-состояния должны быть визуально различимы.
- Выбранную компонентную библиотеку и стратегию стилей необходимо зафиксировать в README или архитектурных заметках.

## 11. Требования к модели данных

Основные моковые сущности:

- аукцион;
- ставка;
- локальный справочник городов для фильтров.

Организатор, груз, маршрут, точки маршрута, условия оплаты, торговые параметры и ограничения являются вложенными частями DTO аукциона, а не отдельными API-сущностями.

Seed-данные должны покрывать минимум следующие сценарии:

- разные типы и статусы аукционов;
- разные пользовательские статусы;
- аукцион без ставок;
- аукцион со скрытой историей ставок;
- аукцион без возможности ставки;
- аукцион с `min/max/step`;
- отменённая ставка с причиной;
- победившая и непобедившая ставка;
- скрытые контакты/адреса и скрытая цена груза.

Количество seed-записей явно не задано и определяется достаточностью для проверки пагинации и перечисленных состояний.

## 12. Источник данных и хранение

Источники требований:

1. `openapi.auctions.v0.json` — обязательный источник API-контрактов.
2. PDF-тестовое задание — источник требований к UI и процессу сдачи.
3. Готовые fixtures от HR, если они будут предоставлены.

Если готовых fixtures нет, данные генерируются самостоятельно строго по OpenAPI-схеме.

MSW использует in-memory store на время работы приложения. Поведение после перезагрузки страницы пока не определено.

## 14. Критерии готовности

- Проект запускается локально по инструкции README.
- Использован обязательный стек.
- Все четыре endpoint’а представлены в MSW.
- Запросы и ответы соответствуют OpenAPI-схеме.
- Список имеет pagination, filters, skeleton, empty и error states.
- Detail получает данные через отдельный endpoint.
- Bets получает данные через отдельный endpoint.
- Форма ставки валидируется через React Hook Form + Zod.
- Успешная ставка меняет mock store и отображается в связанных местах.
- После mutation инвалидируются list/detail/bets queries.
- Обрабатывается `422`.
- Учтены `can_set_bet`, `hide_bets_history`, `hide_points_address_and_contacts`, `no_view_cargo_price`.
- Реализован prefetch detail по intent/hover.
- Интерфейс работает на desktop и mobile.
- React component-файлы имеют суффикс `.component.tsx`.
- В репозитории есть README и `AI_USAGE.md`.

## 15. Спорные места и риски

До реализации нужно принять следующие решения:

1. Предоставит ли HR готовые fixtures, примеры JSON-ответов или только OpenAPI-схему?
2. Если fixtures будут предоставлены, нужно ли использовать их без изменений или допускается дополнять их edge cases?
3. Какой вариант хранения фильтров выбрать: URL search params или localStorage? Для проверяемости предпочтительнее URL.
4. Нужно ли сохранять состояние MSW после перезагрузки страницы или достаточно in-memory store?
5. Какой именно URL и формат использовать для режима установки ставки: отдельный route или query parameter?
6. Нужна ли отдельная страница ставок или достаточно вкладки/секции на detail-странице?
7. Как трактовать «изменить ставку»: использовать тот же `POST` endpoint и создавать новую ставку либо имитировать замену собственной ставки в store?
8. Требуется ли реальная авторизация пользователя или достаточно фиксированного mock-пользователя?
9. Какой UI-kit и подход к стилям выбрать?
10. Какой минимальный набор браузеров и viewport’ов проверять?
11. Нужны ли автоматические тесты UI или достаточно тестов чистой логики, которые в задании обозначены как желательные?
12. Нужно ли генерировать все возможные enum-состояния из схемы или достаточно набора, покрывающего основные UI-сценарии?
13. Как отображать цену, если `no_view_cargo_price` скрывает цену груза: скрывать только цену груза или также торговые цены?
14. Какой UX использовать при скрытых адресах и контактах: placeholder, пояснение или полное исключение блока?
15. Как обрабатывать ошибки `401`, если авторизация не реализуется: общий error state, toast или mock-страница авторизации?
